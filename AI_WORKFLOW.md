# AI Workflow Note

## Tools actually used
- **Claude Code (Claude Sonnet 5.5)** — planning, scaffolding, implementation, test writing, debugging and documentation for this project, working directly in a Linux sandbox with shell access (npm, headless Chrome).
- No other AI tools (no Copilot, Cursor, ChatGPT, image generators) were used for this build.

## Where AI materially sped things up
- **Scaffolding and boilerplate:** project config, Tailwind/ESLint/TS setup, route handlers, Zod schemas and the dashboard/editor UI came together in a single pass.
- **Test generation:** the permission matrix (owner/editor/viewer/no-access) and import edge cases were enumerated and encoded as 17 tests quickly.
- **Browser e2e script:** AI wrote a 15-step Playwright script and ran it against the production build, which is much more thorough than I would normally script by hand in the same time.
- **Documentation:** README, architecture and submission files were drafted from the actual code and then checked against it.

## What AI-generated output was changed or rejected
- **Prisma → Drizzle/libSQL.** The first schema used Prisma + SQLite (the stack suggested in the brief). `prisma db push` failed because the sandbox blocks Prisma's engine download, so that code was discarded rather than worked around. Drizzle + libSQL also solves persistence on Vercel (local file ⇄ Turso with one driver), so it is a better fit than the original plan.
- **Underline extension:** the initial dependency list included `@tiptap/extension-underline`; TipTap 3's StarterKit already bundles it, so the extra dependency was removed.
- **401 handling bug.** The first API client redirected to `/login` on any 401. The browser e2e test showed this reloaded the login page and swallowed the "Incorrect email or password" message. Fixed by excluding `/api/auth/*` from the redirect, then re-ran the whole suite.
- **Missing TypeScript CSS declaration** (TS 6 flags side-effect CSS imports): added `src/css.d.ts` after the first build failed.
- **Prompt scope trimmed:** the prompt asked for screenshots, deployment and a walkthrough video. Screenshots are generated by the e2e script.

## How correctness was verified (what was actually run)
- `npm test` — 17 Vitest tests against a real temporary SQLite database: create/save/retrieve with formatting preserved, 404 for non-members, editor/viewer/owner rules, revoke, delete cascade, search escaping, import success + rejection paths, validation.
- `npm run typecheck`, `npm run lint`, `npm run build` — all clean.
- `curl` checks against the production server for auth, 401/403/404/400/413/415 responses, a real `.docx` import, and **a server restart** confirming documents and shares persisted.
- Browser e2e (`npm run e2e`) in headless Chrome: 15 checks covering the full user flow, plus a visual review of the generated screenshots for layout quality.

## What still needs human judgment (not claimed as done)
- Choosing to cut real-time collaboration, sign-up and export, and the trade-offs documented in `ARCHITECTURE.md` should be reviewed and owned by the candidate.
- Manual exploratory testing by a person (keyboard-only use, screen readers, other browsers) has **not** been done; only headless Chrome was exercised.
